# selfhost-coverage — покрытие self-hosted компилятора Latent

Инструмент измеряет, какие функции `selfhost/shc.lat` реально исполняются,
когда компилятор прогоняет корпус программ. Zero dependencies, Node ESM,
работает на Windows и Unix.

```bash
# из корня репозитория
node tooling/selfhost-coverage/run.mjs

# отчёт в JSON/Markdown, порог 90% (exit 1, если ниже)
node tooling/selfhost-coverage/run.mjs --min 90

# инструментированный компилятор + приблизительное покрытие инструкций
node tooling/selfhost-coverage/run.mjs --lines --out coverage.wasm
```

## Зачем

`selfhost/` уже проверяется фиксированной точкой (`stage2 === stage3`) и
дифференциальными тестами, но эти проверки не отвечают на вопрос «какой код
компилятора вообще исполняется тестами». Инструмент даёт:

* **function coverage** — доля функций верхнего уровня `shc.lat`, вызванных
  хотя бы один раз на корпусе (обязательная метрика, порог `--min`);
* **приблизительное line coverage** (`--lines`) — доля инструкций верхнего
  уровня функций, до которых дошло исполнение;
* список непокрытых функций с файлом/строкой — это готовый backlog для
  дифференциальных тестов;
* **fidelity-проверку**: инструментированный компилятор обязан выдавать
  побайтово те же программы, что и неинструментированный. Иначе
  инструментация изменила семантику, и отчёту нельзя верить.

## Как это работает

### 1. Инструментация исходника

`run.mjs` читает собранный `selfhost/shc.lat` (или собирает его из
`--src selfhost/src`) и вставляет в начало тела каждой функции верхнего
уровня вызов `cov_bump(ID)`:

```latent
fn tokenize() -> int { cov_bump(41);
    ...
}
```

Функции верхнего уровня находятся сканером (`src/instrument.mjs`), который
учитывает:

* глубину фигурных скобок (лямбды внутри тел не инструментируются);
* строковые литералы и escape-последовательности;
* линейные `//` и **вложенные** блочные `/* ... */` комментарии;
* `async fn` и однострочные функции;
* объявления типов `fn(int) -> int` (не считаются функциями).

Сканер не является полным парсером Latent — этого достаточно, потому что в
`shc.lat` все компиляторные функции объявлены на верхнем уровне. Если
появится функция с телом нестандартной формы, инструментатор либо не найдёт
её (она попадёт в «непокрытые»), либо упадёт с понятной ошибкой — молча
портить исходник он не должен.

В преамбулу инструментированного файла добавляются:

```latent
fn cov_bump(id) -> int { let a = 32768 + id * 4; store32(a, load32(a) + 1); return 0; }
fn cov_read(id) -> int { return load32(32768 + id * 4); }
fn cov_line(id) -> int { ... }   // только при --lines
```

### 2. Где живут счётчики и почему там

Счётчики — обычные `i32` в линейной памяти инструментированного компилятора.
Адреса выбраны так, чтобы не пересечься с картой ABI `shc` (`00_abi.lat`):

| Диапазон | Что там | Комментарий |
|---|---|---|
| `0..1023` | нулевая страница / `null` | не трогаем |
| `1024..` | data-секция скомпилированного компилятора | строковые литералы; на практике < 4 КиБ |
| **`32768..65535`** | **счётчики покрытия** | **свободный диапазон** |
| `65536..` | `OUTB` — готовый WASM | занято компилятором |
| `262144..` | `SCRB`/`FNB`/`BODYC`/`CODEB` | рабочие буферы |
| `1245184..` | таблицы `KIND/TVAL/.../ERRB` | см. `00_abi.lat` |
| `3145728..` | `INPUT` — входной исходник | 128 КиБ + |
| `3407872..` | таблицы классов/enum/лямбд/тайп-чекера | см. `00_abi.lat` |

Почему именно `32768`:

* старый адрес `INPUT` (`32768`) больше не используется — `INPUT()` теперь
  `3145728`; диапазон `32768..65535` — единственная «дыра» в карте памяти,
  которая не пересекается ни с одной областью компилятора;
* диапазон целиком помещается в **начальную** память модуля (16 страниц =
  1 МиБ), поэтому счётчики доступны ещё до `alloc(4600000)` в драйвере;
* `data`-секция компилятора заканчивается намного ниже (единицы КиБ), а
  `OUTB` начинается ровно с `65536`.

Раскладка:

```text
[32768 .. 49152)  — 4096 счётчиков функций  (ID 0..4095)
[49152 .. 65536)  — 4096 счётчиков строк    (ID 4096..8191)
```

Это 8192 `i32` = 32 КиБ. Если функций/инструкций станет больше, инструмент
падает с явной ошибкой (`FUNCTION_CAP`/`LINE_CAP`) — тогда нужно расширять
диапазон и обновлять этот раздел, а не молча затирать память.

> **Проверка при изменениях ABI.** Если в `00_abi.lat` появится новая область
> ниже `65536` или изменится начальный размер памяти, константы
> `COUNTER_BASE`/`LINE_ID_BASE` в `src/instrument.mjs` нужно пересмотреть.
> Покрытие — диагностический инструмент, а не часть рантайма; его адреса не
> входят в ABI компилятора.

### 3. Сборка инструментированного компилятора

`--builder`:

| Значение | Поведение |
|---|---|
| `auto` (по умолчанию) | `latentc`, если найден; иначе `selfhost/stage1.wasm` |
| `latentc` | нативный Rust-компилятор (`--latentc`, env `LATENTC`, `target/debug/latentc[.exe]`) |
| `stage1` | `selfhost/stage1.wasm` (быстро: selfhost компилирует сам себя за миллисекунды) |
| `<path>.wasm` | готовый компилятор |

`latentc` — авторитетный путь: он собирает инструментированный исходник
независимо от того, насколько свеж `stage1.wasm`. `stage1` удобен в тестах и
на машинах без Rust, но может быть старее `shc.lat` (инструмент предупреждает
об этом).

### 4. Корпус

Корпус собирается из нескольких источников (`src/corpus.mjs`):

1. **все кейсы `selfhost/test/*.test.mjs`** — из каждого объекта берётся
   `src:`-шаблон (template literal), раскрываются JS-escape;
2. **сам `shc.lat`** — компилятор компилирует себя (самый полный вход);
3. **`web-ide/examples/*.lat`** — реальные программы языка (включая
   host-примеры, которые дают ошибку, но проходят лексер/парсер/тайп-чек);
4. **ручные пробы** (`PROBES` в `src/corpus.mjs`) — классы, enum, match,
   лямбды, float, строки, память, host-конструкции, ветки ошибок
   (`undefined variable/function`, arity, return mismatch, unknown
   field/class/method, host builtins, модуль без `main`);
5. **фаззинг-подобный набор** — детерминированный LCG (без `Math.random`),
   `--fuzz N` программ (по умолчанию 24) из шаблонов, включая заведомо
   ошибочные.

Ошибочная программа — **не** пропуск: компилятор всё равно проходит лексер,
парсер и тайп-чек, и счётчики это фиксируют. «Успех» в отчёте означает
`main() >= 0` и отсутствие трапа; ошибка компиляции — нормальный исход для
error-кейсов.

### 5. Таймауты и защита от зависаний

Известный класс дефектов selfhost — зависание на структурных аннотациях
(`fn f(a: [int])` и т.п.). Корпус не должен вешать весь прогон, поэтому
каждый кейс исполняется в долгоживущем worker-потоке с таймаутом
`--timeout` (по умолчанию 3000 мс). При таймауте worker убивается, кейс
помечается `timeout`, создаётся новый worker. Такие кейсы не дают покрытия и
видны в отчёте (`corpus.timedOut`).

### 6. Fidelity

Для каждого кейса, на котором **неинструментированный** компилятор
завершился, инструментированный обязан дать **тот же результат и те же
байты** выходного WASM (сравниваются SHA-256). Это ловит:

* случайно изменённую семантику при вставке `cov_bump`;
* порчу памяти счётчиками;
* рассинхронизацию инструментатора с синтаксисом.

Если есть расхождения, `run.mjs` печатает их и завершается с кодом `1`.
Fidelity сравнивает не с Rust-эталоном, а с **тем же** selfhost-компилятором
без инструментации — это проверка инструмента, а не паритета.

## Методика измерения

### Function coverage (обязательная)

* Единица — **функция верхнего уровня** `shc.lat` (включая однострочные
  аксессоры вроде `INPUT()`, `KIND()`).
* Функция покрыта, если её счётчик `> 0` хотя бы на одном кейсе корпуса.
* Процент = `покрытые / все функции`. Это консервативная метрика: она не
  говорит, что все ветки функции исполнены.
* Порог `--min` применяется именно к ней.

### Line coverage (`--lines`, приблизительная)

* Счётчик ставится в начало **инструкции верхнего уровня** внутри тела
  функции: `let`, `return`, `if (`, `while (`, `for (`, `spawn`, `yield`,
  `select`, `test`, вызов/присваивание/индексация по имени.
* Не инструментируются: `}`, `else`, `case`, `default`, продолжения
  выражений, строки внутри скобок, комментарии, пустые строки.
* Одна строка — один счётчик; если на строке несколько инструкций, покрытие
  строки засчитывается по первой. Многострочные выражения относятся к первой
  строке.
* Это **не** branch coverage и не покрытие всех байтов кода. Полный
  statement-level парсер не используется сознательно: инструментация не
  должна менять семантику. Fidelity-проверка подтверждает это на корпусе;
  при сомнениях запускайте без `--lines` (функциональное покрытие — основной
  критерий).

Почему не instrumentation каждой инструкции по байткоду: у нас нет доступа к
байткоду компилятора до его исполнения (компилятор — это WASM, собранный из
`.lat`), а инструментация на уровне исходника — единственный способ не
зависеть от внутренностей WASM-эмиттера. Строчный режим — компромисс,
дающий полезную картину без полноценного парсера.

## Отчёт

По умолчанию пишутся:

* `tooling/selfhost-coverage/coverage.json` — машиночитаемый;
* `tooling/selfhost-coverage/coverage.md` — для людей.

Пути переопределяются `--json` и `--md`. Позже эти файлы можно направлять в
`selfhost/coverage-report.md` (например, в CI-артефакт) — сам инструмент
ничего не пишет в `selfhost/`, чтобы не засорять дерево компилятора.

### JSON (основные поля)

```jsonc
{
  "tool": "selfhost-coverage",
  "version": 1,
  "generatedAt": "2026-11-02T…",
  "source": { "path": ".../shc.lat", "mode": "shc", "parts": [], "bytes": 167798, "sha256": "…" },
  "builder": { "kind": "latentc", "path": ".../latentc.exe", "bytes": 59784 },
  "instrumentation": {
    "lines": false, "functions": 369, "lineCounters": 0,
    "counterBase": 32768, "lineCounterBase": 49152, "bytes": 213147
  },
  "corpus": { "total": 219, "ok": 170, "failed": 49, "trapped": 0, "timedOut": 7,
              "byKind": { "test": 140, "self": 1, "example": 24, "probe": 30, "fuzz": 24 } },
  "functions": {
    "total": 369, "covered": 369, "percent": 100,
    "uncovered": [],
    "byPart": [ { "part": "00_abi.lat", "total": 88, "covered": 88, "percent": 100 } ]
  },
  "lines": null,                 // или { total, covered, percent, uncovered, byPart }
  "fidelity": { "checked": 212, "mismatches": [] },
  "gate": { "min": 90, "metric": "functions", "passed": true },
  "corpusCases": [ { "name": "parity.test.mjs:59", "kind": "test", "ok": true, "ret": 1113, "functionsHit": 118 } ]
}
```

Как читать:

* `functions.covered/total/percent` — главная цифра;
* `functions.uncovered` — что добавить в тесты (сначала смотрите на функции
  с содержательной логикой, а не на one-line константы);
* `functions.byPart` — где концентрация непокрытого кода;
* `corpus.timedOut` — известные зависания (инструмент их переживает, но
  покрытия они не дают);
* `fidelity.mismatches` — **ненулевое значение означает баг инструментации**,
  а не «плохое покрытие»; прогон в этом случае завершается кодом 1.

Markdown-отчёт содержит сводку, таблицу по частям, ASCII-бар, список
непокрытых функций, раздел fidelity и разбивку корпуса.

## CLI

```text
node tooling/selfhost-coverage/run.mjs [опции]

  --shc <path>         собранный компилятор (по умолчанию selfhost/shc.lat)
  --src <dir>          собрать компилятор из частей selfhost/src
  --out <path>         сохранить инструментированный компилятор (.wasm)
  --json <path>        JSON-отчёт (по умолчанию tooling/selfhost-coverage/coverage.json)
  --md <path>          Markdown-отчёт (по умолчанию tooling/selfhost-coverage/coverage.md)
  --min <n>            порог покрытия функций в %, exit 1 если ниже (по умолчанию 0)
  --builder <kind>     auto | latentc | stage1 | <path к .wasm>
  --latentc <path>     путь к нативному latentc (или env LATENTC)
  --tests <dir>        каталог selfhost-тестов (по умолчанию selfhost/test)
  --no-tests           не брать кейсы из тестов
  --no-examples        не брать web-ide/examples
  --no-fuzz            не генерировать фаззинг-корпус
  --fuzz <n>           число фаззинг-программ (по умолчанию 24)
  --timeout <ms>       таймаут одного прогона компилятора (по умолчанию 3000)
  --lines              включить приблизительное покрытие инструкций
  --instrumented <p>   сохранить инструментированный исходник .lat
  --keep               не удалять временные файлы
  --quiet              только итоговая строка
```

Коды выхода:

| Код | Значение |
|---|---|
| `0` | отчёт построен, покрытие ≥ `--min`, fidelity без расхождений |
| `1` | покрытие ниже `--min` **или** есть расхождения fidelity |
| `2` | ошибка инструмента/сборки (нет `--shc`, не собран `latentc`/`stage1`, инструментированный компилятор невалиден и т.п.) |

## Ограничения

1. **Function coverage не равна branch coverage.** Функция может быть
   покрыта одной веткой; для веток нужны дифференциальные кейсы, а не
   счётчик на входе.
2. **Строчное покрытие приблизительное** (см. методику). Оно полезно для
   поиска мёртвых участков, но не является юридически точным «line
   coverage».
3. **Инструментированный компилятор содержит 2–3 дополнительные функции**
   (`cov_bump`, `cov_read`, `cov_line`). Их индексы сдвигают индексы
   компиляторных функций, но на выходной WASM это не влияет — fidelity это
   проверяет. Сами `cov_*` в отчёт не входят.
4. **Fidelity — не паритет.** Сравнение идёт с неинструментированным
   selfhost-компилятором, а не с Rust-эталоном. Паритет проверяют
   `selfhost/test/parity.test.mjs` и `latent-work/gap-matrix.mjs`.
5. **Таймауты не дают покрытия.** Кейс, на котором компилятор завис,
   помечается `timeout`; это сигнал о дефекте, а не о покрытии.
6. **Зависимость от карты памяти.** Диапазон `32768..65535` выбран для
   текущего `00_abi.lat`. При изменении карты памяти обновите константы и
   этот README.
7. **Ёмкость 4096 функций + 4096 строк.** При превышении инструмент падает
   с явной ошибкой; расширение — новая раскладка (и проверка, что она не
   пересекает ABI).
8. **Нет измерения host-рантайма.** `print`, каналы, AI-примитивы в
   selfhost — заглушки/ошибки; инструмент измеряет только компилятор.
9. **`stage1` может быть старым.** Всегда проверяйте предупреждение
   `builder.stale`; для точных цифр используйте `--builder latentc` или
   пересоберите `stage1` через `node selfhost/bootstrap.mjs`.

## Тесты инструмента

```bash
node --test "tooling/selfhost-coverage/test/*.test.mjs"
```

27 тестов, ~1 с (интеграционный CLI-тест использует `--builder stage1`):

* `instrument.test.mjs` — сканер верхнего уровня (строки/комментарии/типы/
  `async fn`), ID, вставки, строчные кандидаты, конфликты имён;
* `report.test.mjs` — проценты, byPart, uncovered, порог, Markdown;
* `cli.test.mjs` — строчная инструментация не меняет результат программы,
  счётчики читаются из памяти, полный CLI-прогон даёт валидный отчёт и
  fidelity 0, `--src` совпадает с `build.mjs`, ошибочный `--shc` → код 2,
  `--min 100` → код 1.
