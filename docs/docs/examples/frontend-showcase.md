# Интерактивные демо: Latent против JS

Этот раздел — не про «hello world». Здесь Latent компилируется в WebAssembly и
выполняет настоящую нагрузку прямо на странице: миллионы целочисленных операций,
пиксели `ImageData` и гравитацию для десятков тысяч частиц. Рядом с каждым демо
лежит исходник `.lat`, а цифры измеряет **ваш** браузер, а не автор статьи.

Демо — статические страницы без сборщика и внешних зависимостей. Они живут в
`docs/static/demos/` и публикуются по адресам `/latent/demos/...`.

Симуляция целиком живёт в памяти модуля: четыре массива `i32` (x, y, vx, vy) по
фиксированным смещениям, никаких объектов на частицу. JS-хост читает эти числа
как `Int32Array` и рисует их на canvas — без сериализации и без `postMessage`.

## Ключевые фрагменты

### FNV-1a: байты и переполнение i32

```latent
// FNV-1a over a 1 MiB byte buffer, `rounds` passes.
fn main(n: int, rounds: int) -> int {
    let ptr = load32(8);
    if (ptr == 0) {
        ptr = alloc(n + 8);
        store32(8, ptr);
        let s = 123456789;
        let g = 0;
        while (g < n) {
            s = (s * 1103515245 + 12345) & 2147483647;
            store8(ptr + g, (s >> 8) & 255);
            g = g + 1;
        }
    }

    // 0x811c9dc5 as a signed i32: literals above 2^31 - 1 wrap.
    let h = 0 - 2128831035;
    let r = 0;
    while (r < rounds) {
        let i = 0;
        while (i < n) {
            h = (h ^ load8(ptr + i)) * 16777619;
            i = i + 1;
        }
        r = r + 1;
    }
    return h;
}
```

Обратите внимание на `0 - 2128831035` вместо `2166136261`: литерал больше
`2^31 - 1` в i32-пути заворачивается, и запись знаковым числом делает поведение
очевидным. JS-двойник использует `Math.imul` с тем же знаковым начальным
значением — контрольные суммы совпадают.

### Пиксели: `load8`/`store8` вместо объектов

```latent
fn luma(r: int, g: int, b: int) -> int {
    return (77 * r + 150 * g + 29 * b) >> 8;
}

fn gray(src: int, dst: int, size: int) {
    let i = 0;
    while (i < size) {
        let v = luma(load8(src + i), load8(src + i + 1), load8(src + i + 2));
        store8(dst + i, v);
        store8(dst + i + 1, v);
        store8(dst + i + 2, v);
        store8(dst + i + 3, 255);
        i = i + 4;
    }
}
```

`src` и `dst` — обычные `i32`-адреса в линейной памяти. Хост один раз копирует
`ImageData` в память модуля, а результат оборачивает в `new ImageData(view)` —
`putImageData` читает память WASM напрямую.

### Гравитация: фиксированная точка без `sqrt`

```latent
// Упрощённый фрагмент particles.lat: сила одного аттрактора.
fn attractor_force(x: int, y: int, ax: int, ay: int, gravity: int, vx: int, vy: int) -> int {
    let dx = ax - x;
    let dy = ay - y;
    let d2 = dx * dx + dy * dy;
    if (d2 < 90000) {
        return vx;
    }
    let f = (gravity << 24) / (d2 + 40000);
    return vx + ((dx * f) >> 13) - ((dy * f) >> 13);
}
```

Позиции хранятся в 1/16 пикселя, скорости — в 1/256 пикселя за шаг. Сила —
смягчённая обратная квадратичная, но без `sqrt` и `float`: только `i32`,
деление и сдвиги. Именно поэтому JS-двойник может воспроизвести траектории
бит в бит — это проверяется кнопкой **Parity**.

## Как это устроено

```
docs/static/demos/
├── index.html              # хаб демо
├── assets/
│   ├── demo.css            # общий тёмный shell
│   ├── wasm.js             # fetch/instantiate, C-ABI компилятора
│   ├── bench.js            # JS-двойники пяти бенчмарков
│   ├── imaging.js          # JS-двойники фильтров
│   ├── physics.js          # JS-двойник интегратора
│   └── highlight.js        # подсветка .lat
├── bench/                  # index.html + 5 *.lat + 5 *.wasm
├── image/                  # index.html + filter.lat + filter.wasm
├── physics/                # index.html + particles.lat + particles.wasm
├── compiler.wasm           # копия для кнопки «compile in browser»
└── build-demos.mjs         # .lat → .wasm + smoke-run
```

1. **Сборка модулей.** `build-demos.mjs` загружает `web-ide/compiler.wasm`,
   вызывает C-ABI `latent_alloc` / `latent_compile` / `latent_free` и пишет
   рядом с каждым `.lat` готовый `.wasm`. Затем каждый модуль инстанцируется и
   один раз исполняется — это дымовой тест.
2. **Загрузка на странице.** `wasm.js` фетчит `.wasm`, создаёт
   `WebAssembly.Instance` с единственным импортом `env.print(i32)` и отдаёт
   `exports.main` и `exports.memory`.
3. **Передача данных.** Массивы и строки — это байты по указателю:
   `[len u32][i32…]` и `[len u32][utf8…]`. Никакого JSON и никакой
   сериализации: JS пишет в `Uint8Array` поверх `memory.buffer`, модуль читает
   те же байты.
4. **Компиляция в браузере.** Кнопка на странице бенчмарка скачивает
   `sieve.lat`, компилирует его тем же `compiler.wasm` за единицы миллисекунд и
   запускает результат. Это тот же компилятор, что в playground, просто
   вызванный из обычной статической страницы.

Полный ABI описан в [WASM ABI](../reference/wasm-abi.md), а базовый сценарий
«JS-хост + `.wasm`» — в [Canvas и кадры](./frontend-canvas.md).

## Почему Latent, а не просто JS

Честный ответ: **не всегда**. JavaScript-движки сегодня отлично оптимизируют
типизированные массивы и целочисленные циклы, а на коротких вызовах накладные
расходы на переход JS↔WASM могут съесть выигрыш. Демо показывает и это — если
JavaScript окажется быстрее, вы увидите соответствующую подпись, а не спрятанную
цифру.

Где выигрыш реальный:

- **Контроль памяти.** `alloc` — это явное выделение в линейной памяти. Нет
  объектов на частицу, нет скрытых аллокаций в цикле, нет сборщика мусора.
  Для canvas, аудио и игр важна не средняя скорость, а отсутствие редких
  GC-пауз и стабильный p95 кадра.
- **Предсказуемые целые числа.** `int` — это ровно `i32`: переполнение,
  сдвиги и деление определены. Результат не зависит от того, как JIT решил
  оптимизировать ветку в этот раз.
- **Один буфер вместо графа объектов.** 30 000 частиц — это 480 КБ памяти и
  четыре `Int32Array`-вью. Кэш-локальность и отсутствие разыменований дают
  ровный шаг симуляции.
- **Песочница.** У модуля нет доступа к DOM, сети или cookie. Если вы
  исполняете сгенерированный или недоверенный код, WASM ограничивает его
  ровно той памятью, которую вы сами выделили.
- **Compiler-as-WASM.** Компилятор Latent собран в WebAssembly. Исходник можно
  превратить в модуль на клиенте, без сервера и без установленного toolchain.

Чего в демо **нет**:

- попарных столкновений частиц (используются столкновения с ядрами
  аттракторов и стенками) — это O(N·3), а не O(N²);
- фонового Worker: всё считается на главном потоке, чтобы сравнение было
  честным и измеримым;
- обещания «WASM быстрее всегда». Цифры на странице — живые.

## Запуск и проверка

Демо не требуют сборки. Достаточно отдать `docs/static/` любым статическим
сервером:

```bash
# из корня репозитория
python -m http.server 8000 --directory docs/static
# откройте http://localhost:8000/demos/
```

Пересобрать `.wasm` после правок `.lat`:

```bash
node docs/static/demos/build-demos.mjs            # компиляция + smoke-run
node docs/static/demos/build-demos.mjs --no-verify
```

Скрипт использует `web-ide/compiler.wasm` (переопределяется переменной
`LATENT_COMPILER_WASM`). Кнопка «compile in browser» берёт
`docs/static/demos/compiler.wasm`, а если его нет — пытается загрузить
`/latent/playground/compiler.wasm`; на опубликованном сайте playground
синхронизируется скриптом `scripts/sync-playground.mjs`.

Все ```latent-блоки этой страницы проверяются
`docs/scripts/validate-examples.mjs`; сборка сайта — `pnpm run build` в
`docs/`.

## Что попробовать

1. В бенчмарке нажмите **«Прогнать все 5»** и сравните порядок величин на
   своей машине. Затем переключите вкладку и вернитесь — цифры не «зашиты».
2. В демо изображений включите **Sobel** и подвигайте ползунок сравнения с
   оригиналом: видно, что фильтр работает поверх RGBA, а не поверх CSS.
3. В физике поставьте 30 000 частиц и гравитацию 50 — шаг симуляции всё ещё
   измеряется в микросекундах, а canvas остаётся на 60 fps.
4. Нажмите **Parity** в физике: JS-двойник и WASM пройдут 120 шагов и должны
   совпасть бит в бит. Если реализации разойдутся, бейдж станет красным.
