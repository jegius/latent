# Операторы

Источники: `src/parser/expressions/core.rs` (приоритеты),
`src/codegen/emit_expr.rs` (`compile_binary`, `compile_string_operand`),
`web-ide/compiler/interpreter-expressions.js` (движок №1).

Общая оговорка: **тайпчекер почти не проверяет операнды** (см.
[типы](./types.md#что-typechecker-игнорирует)), поэтому выбор WASM-инструкции в
кодогене определяется *статической* оценкой типа операндов, а не аннотациями.
Это причина многих «странностей» ниже.

## Таблица операторов

|---|---:|---:|---|---|---|

## Арифметика

- **Числа в Latent — «числовые»**: тип `int`/`float` тайпчекер считает
  совместимыми в обе стороны (`unify` в `src/typechecker/types/mod.rs`).
  Во время кодогенерации операнды приводятся неявно только если оба статически
  `Float`; в остальных случаях используется `i32`-путь.
- `+` над `int` — сложение `i32`; над `float` — `f64.add`; **если хотя бы один
  операнд статически `string` — конкатенация**: числа конвертируются в строки
  (`__latent_i32_to_str`, `__latent_f64_to_str`), массивы/функции — нет.
- `/` — целочисленное деление `i32.div_s` для int (`17 / 5 == 3`) и `f64.div`
  для float. Деление на ноль в WASM — **trap** (`unreachable` при исполнении).
- `%` — `i32.rem_s` всегда, даже когда операнды float; на float-выражениях это
  даёт **невалидный WASM** (см. дефекты ниже).

```latent
fn main() -> int {
    print(17 / 5);      // 3
    print(17 % 5);      // 2
    print("v" + 1);     // v1 (int -> string)
    return 0;
}
```

Движок №1: `+ - * / %` — обычная JS-арифметика; `17 / 5` даёт `3.4`,
`+` над массивами — конкатенация массивов, `+` со строкой — конкатенация
(`String(left) + String(right)`).

## Сравнения и равенство

- Для чисел в движке №2 используются знаковые `i32`-сравнения или `f64`-сравнения
  в зависимости от статического типа.
- Для строк `==`/`!=` сравнивают **содержимое** (`__latent_str_eq`, побайтово);
  `<`, `>`, `<=`, `>=` на строках сравнивают указатели (`i32.lt_s`), а не
  лексикографически.
- Для остальных значений (`bool`, массивы, enum, классы) `==` — сравнение
  представления: `i32.eq`. Для массивов это сравнение **указателей**.
- Результат сравнения — `i32` 0/1 (напечатается как `0`/`1`).
- Цепочка `a < b < c` парсится и компилируется как `(a < b) < c`, т.е.
  сравнение `0/1` с `c`; тайпчекер ошибки не выдаёт.

```latent
fn main() -> int {
    print("ab" == "ab");     // 1 (сравнение содержимого)
    print(2 > 1);            // 1
    let a = [1];
    let b = [1];
    print(a == b);           // 0 — сравниваются указатели, а не элементы
    return 0;
}
```

Движок №1: `==`/`!=` — глубокое структурное равенство (`deepEqual`): массивы и
вложенные массивы сравниваются поэлементно, строки — по значению, тензоры — по
форме и данным. `<`/`>` для строк — лексикографическое сравнение JS.

## Логические операторы и короткое замыкание

`&&` и `||` вычисляются с **коротким замыканием** в обоих движках:

- движок №2: `a && b` → `if a { b != 0 } else { 0 }`; `a || b` →
  `if a { 1 } else { b != 0 }`; результат всегда `i32` 0/1;
- движок №1: результат — `true`/`false`, правда по truthiness
  (`0`, `null`, `false` — ложь; пустой массив — истина).

```latent
fn main() -> int {
    let ok = false && (1 / 0 > 0);   // правая часть не вычисляется
    if (ok) { return 1; }
    return 0;
}
```

Правый операнд во время компиляции всё равно компилируется, поэтому ошибки
кодогена в невыполняемой ветке (например host-примитив) проявятся на этапе
компиляции.

## Побитовые операции и сдвиги

Поддерживаются только движком №2 (в AST: `BitAnd`, `BitOr`, `BitXor`, `Shl`,
`Shr`). Результат — `int`. Движок №1 не умеет лексировать `&`, `|`, `^`, `<<`,
`>>` — это ошибка «Unexpected character».

```latent
fn main() -> int {
    let a = 6 & 3;      // 2
    let b = 6 | 3;      // 7
    let c = 6 ^ 3;      // 5
    let d = 1 << 4;     // 16
    let e = 16 >> 2;    // 4
    return a + b + c + d + e;
}
```

Сдвиг влево/вправо — 32-битный; `>>` арифметический (`i32.shr_s`). Приоритет
сдвигов выше сложения: `1 << 2 + 3` = `1 << 5` = 32.

## Присваивание

Присваивание — **выражение** с правой ассоциативностью и приоритетом 2 (ниже
`||`):

- цель: имя (`x = e`), элемент массива (`a[i] = e`), поле (`o.f = e`);
- результат — присвоенное значение (кодоген оставляет его на стеке), так что
  `let y = (x = 5);` даёт `y == 5`;
- цепочка `a = b = 3` допустима;
- `a[i] = e` **не проверяет типы** и компилируется в `i32.store` (4 байта);
- `o.f = e` использует layout класса; для `float`-поля — `f64.store`.

```latent
fn main() -> int {
    let a = 0;
    let b = 0;
    a = b = 3;
    print(a);        // 3
    return a;
}
```

Движок №1: присваивание — **инструкция**, не выражение: `let y = (x = 5);` —
ошибка парсинга; `a = b = 3` не поддерживается.

## Инкремент/декремент и составные присваивания

Их нет: `x++`, `--x`, `x += 1`, `x -= 1` не лексируются как операторы
(`+=` разберётся как `+` и `=`). Единственная форма — `x = x + 1`.

## `->`, `=>`, `<-`

- `->` — только в аннотации типа возврата (`fn f() -> int`, `fn(int) -> int`);
  как оператор выражения не существует.
- `=>` — только в лямбде `fn(x) => expr`.
- `<-` — два разных оператора:
  - бинарный: отправка в канал `ch <- v` (приоритет 2, правая ассоц.);
  - унарный префиксный: приём из канала `<-ch`.
  Оба работают **только в движке №1**; движок №2 при компиляции выдаёт:
  `Оператор отправки в канал (ch <- v) требует host-рантайма движка №1` или
  `Приём из канала (<- ch) требует host-рантайма движка №1`.

## `await`

Префиксный оператор с приоритетом 95. В движке №2 компилируется **прозрачно**:
значение выражения остаётся как есть (`ExprKind::Await` → `compile_expr(inner)`);
типчекер при этом требует, чтобы операнд имел тип `Promise<T>` (у `async fn`
результат оборачивается в `Promise`). Движок №1 разворачивает своё
promise-подобное значение (`{__promise: true, value}`).

## Известные дефекты кодогена, связанные с операторами

Проверено на поставляемой сборке `web-ide/compiler.wasm`:

| Код | Результат |
|---|---|
| `let x: float = 2;` | компилируется, но WASM невалиден |
| `fn f() -> float { return 2; }` | компилируется, WASM невалиден |
| `1 + 2.5` | невалидный WASM (int-литерал → `i32`, float-путь) |
| `1.5 < 2.0` | невалидный WASM (правый `2.0` → `i32.const 2`) |
| `7.5 % 2.0` | невалидный WASM (`i32.rem_s` на f64) |
| `print(sqrt(16))`, `int(sqrt(16))` | невалидный WASM (`sqrt` в f64-контексте валиден, как `int` — нет) |
| `sqrt(2.25)` в `print` | может быть невалиден (выбор конверсии по `StaticTy`) |

Правило: float-выражения валидны, только если **все** участвующие литералы
имеют **ненулевую** дробную часть, а результат не сравнивается с
целочисленным литералом. `2.0`, `5.0`, `1e3` кодоген трактует как `int` и
ломает f64-контекст. Подробнее —
[диагностики и дефекты](./errors.md#известные-ограничения-движка-2-компилируется-но-невалидный-wasm).
