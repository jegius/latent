# Глава 9. Тесты и контракты

## `test`-блоки

```latent
fn factorial(n: int) -> int {
    if (n <= 1) {
        return 1;
    }
    return n * factorial(n - 1);
}

test "factorial" {
    assert(factorial(5) == 120);
    assert_eq(factorial(0), 1);
}

test "arithmetic" {
    assert(2 + 2 == 4);
    assert_eq(2 * 3, 6);
}

fn main() -> int {
    assert(factorial(5) == 120);
    print("factorial(5):", factorial(5));
    return 0;
}
```

Синтаксис:

```text
test "имя" { ... }
test("имя") { ... }
```

- имя обязательно и должно быть строкой (`test 42 { }` — ошибка парсинга);
- блоки объявляются на верхнем уровне;
- `assert(cond)` и `assert_eq(a, b)` — встроенные функции; необязательное
  третье сообщение игнорируется кодогенератором;
- в движке №1 `assert` бросает ошибку исполнения, `assert_eq` — структурное
  сравнение;
- в движке №2 `assert` компилируется в `unreachable` (trap), а `assert_eq`
  сравнивает **i32-значения** (строки/массивы сравниваются по указателям).

## Когда тесты исполняются

| Движок | Верхнеуровневые `test`-блоки |
|---|---|
| №1 (JS) | Исполняются после `main`. Результаты складываются в `interpreter.testResults`, но текущий UI web IDE их **не показывает**; упавший тест не виден в консоли. |
| №2 (Rust → WASM) | Тело типизируется, но **не эмитится**: раннера тестов в WASM-модуле нет. |

Практический вывод: надёжная проверка прямо сейчас — `assert` в `main` или в
вызванной из `main` функции: и движок №1, и движок №2 дадут ошибку
исполнения/тrap при ложном условии.

## `snapshot` и контракты (host-only)

```latent
// Не компилируется движком №2: snapshot и контракты требуют host-рантайма.
fn main() -> int {
    snapshot("demo");
    let c = ai_contract("ordering");
    enforce_contract(c);
    return 0;
}
```

Эти конструкции объявлены в грамматике (`snapshot`, `ai_contract`,
`enforce_contract` — ключевые слова), но их семантика живёт в движке №1 и
AI-гейтвее. В движке №2 они дают ошибку
`Builtin 'snapshot' не поддерживается движком №2 (требует host-рантайма)`.

## Декораторы

```latent
@forall("array")
fn non_empty_length(arr) {
    assert(arr.length >= 0);
}

fn main() -> int {
    return 0;
}
```

Декоратор `@имя(аргументы)` применяется к объявлению. Важно понимать реальное
поведение:

- typechecker прозрачен: проверяется только цель декоратора;
- **на верхнем уровне** кодогенератор видит `Decorator`, а не `Fn`, поэтому
  декорированная функция **не регистрируется**: вызов `non_empty_length(...)`
  из `main` приведёт к `Unknown function: non_empty_length`;
- внутри функции декоратор компилируется как обёртка над целью;
- известные имена `@test`, `@forall`, `@snapshot`, `@ai_contract`,
  `@enforce_contract` не имеют отдельной семантики в Rust-компиляторе — это
  синтаксические маркеры.

Поэтому пример выше компилируется (декоратор не мешает), но использовать
декорированную функцию как обычную нельзя — объявите её без декоратора.

## Ограничения движка №2

- `test`-блоки не исполняются и не влияют на WASM-модуль (кроме проверки типов).
- `assert` — trap при ложном условии; `assert_eq` — побитовое сравнение.
- `snapshot`, `ai_contract`, `enforce_contract` — ошибка host-рантайма.
- Декораторы над `fn`/`class` на верхнем уровне делают цель недоступной для
  вызова.
- Третьи аргументы `assert`/`assert_eq` игнорируются.
