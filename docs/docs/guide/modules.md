# Файловые модули

Модули — это способ разбить программу на несколько `.lat`-файлов и связать их
на этапе компиляции: `export` открывает имя для других файлов, `import`
подключает его. Никакого загрузчика в рантайме нет: линкер собирает один
`Program`, и дальше он идёт в type checker и кодоген так же, как однофайловая
программа. Один и тот же механизм работает в четырёх местах:

| Где | Как |
|---|---|
| Rust-компилятор | `latent::compile_files`, `latentc compile/check` |
| web IDE, движок №1 (JS-интерпретатор) | нативный линкер `web-ide/compiler/modules*.js` |
| web IDE, движок №2 (Rust → WASM) | C-ABI `latent_compile_files` + манифест `LPF1` |
| self-hosted компилятор | `latentc bundle` → плоский исходник (у selfhost нет ФС) |

## 1. Зачем модули

- **Границы ответственности.** `math.lat` с функциями и enum'ами, `model.lat` с
  классами, `main.lat` со сценарием — вместо одного файла на тысячу строк.
- **Проверка на этапе компиляции.** Опечатка в имени, забытый `export`,
  несуществующий файл — ошибка сборки с путём и строкой, а не `undefined` в
  рантайме.
- **Ноль затрат в рантайме.** В WASM не появляется резолвер модулей: имена
  разрешены и переименованы линкером, `import`/`export` в AST уже отсутствуют.
- **Один язык для браузера и сервера.** Тот же проект компилируется в WASM,
  исполняется интерпретатором в playground и уезжает в selfhost через `bundle`.

## 2. Синтаксис

`import` и `export` — объявления **верхнего уровня**. Внутри блока (`{ ... }`)
парсер сообщает об ошибке: `ожидалось 'declaration (import/export допустимы
только на верхнем уровне)'`.

### 2.1. `export`

Модификатор ставится перед top-level `fn`, `class` или `enum` (в том числе перед
`async fn`):

```text
export fn square(x: int) -> int { ... }
export class Point { ... }
export enum Shape { Circle(int), Rect(int, int) }
export async fn fetch(url: string) -> int { ... }
```

- Экспортируются **только** эти три вида: `export let` даёт
  `ожидалось 'fn, class or enum after export'`, а `export` внутри блока или у
  метода класса — `import/export допустимы только на верхнем уровне`.
- Порядок объявлений в файле произвольный: линкер собирает таблицы до
  переписывания AST, поэтому `export fn` может вызывать функцию, объявленную
  ниже, и наоборот.

### 2.2. Именованный импорт

```text
import { square, Point, Shape } from "./math.lat";
import { square as sq } from "./math.lat";
```

- Список — только именованный: `{ name }` или `{ name as alias }`, через запятую.
- `from` и строка пути обязательны, точка с запятой в конце обязательна (в обоих
  движках: это объявление, а не выражение).
- Импорт **разрешает ровно те имена, что перечислены**. `import { Shape }`
  делает видимым и сам `Shape`, и его варианты-конструкторы (`Circle`, `Rect`) —
  они принадлежат enum'у. Остальные имена модуля остаются приватными.
- Импортировать можно только то, что помечено `export`. Приватная функция
  модуля снаружи не видна: `символ 'helper' не экспортирован из 'math.lat'`.
- Алиас — обычное локальное имя: `import { square as sq }` даёт `sq`, а `square`
  в этом файле не появляется.

### 2.3. Импорт ради подключения файла

```text
import "./effects.lat";
```

Форма без списка имён. Так как top-level код в Latent не исполняется, семантика
— «подключить модуль»: файл попадает в проект, разбирается и линкуется (то есть
его ошибки станут ошибками сборки), но имён в текущий модуль не добавляет.

### 2.4. Правила путей

Путь в `import` — это **путь к файлу**, а не имя пакета:

| Правило | Пример | Результат |
|---|---|---|
| только относительный путь | `"./math.lat"`, `"../lib/math.lat"` | разрешается от каталога импортёра |
| расширение `.lat` обязательно | `"./math"` | `путь импорта должен оканчиваться на '.lat'` |
| абсолютные пути запрещены | `"/abs/math.lat"`, `"C:\lib\math.lat"` | `абсолютный путь импорта недопустим` |
| `./` или `../` в начале обязательны | `"math.lat"` | `путь импорта должен быть относительным ('./' или '../')` |
| `..` нормализуется лексически | `"./sub/../math.lat"` | `./math.lat` |
| обратные слэши допустимы | `"..\lib\m.lat"` | `../lib/m.lat` |
| файл загружается один раз | два `import` одного пути | один модуль (canonical path) |

Нормализация — чистая функция (`\` → `/`, схлопывание `.`/`..`/`//`), симлинки
не разрешаются: это важно для WASM-сборки и детерминизма. В web IDE пути
плоские (каталогов нет), поэтому на практике используется `"./name.lat"`;
`../` за пределы workspace даёт ошибку.

### 2.5. Однофайловый API не изменился

`latent::compile_source(&str)` (и C-ABI `latent_compile`) по-прежнему компилирует
один исходник; проект без `import` идёт тем же путём и в `latentc`, поэтому его
WASM байт-в-байт совпадает с прежним (это проверяет golden-набор). Если в
исходнике встретился `import`, возвращается ошибка с подсказкой:

```text
Импорты не поддерживаются в однофайловой компиляции: используйте latent::compile_files / latentc compile <entry.lat> (проект из нескольких файлов)
```

## 3. Проект из трёх файлов

```text
project/
  main.lat    — entry: точка входа, main()
  math.lat    — функции и enum
  model.lat   — класс и функция, использующая math
```

```latent
// module-part math.lat
export fn square(x: int) -> int { return x * x; }

export fn sum_squares(a: int, b: int) -> int { return square(a) + square(b); }

export enum Shape { Circle(int), Rect(int, int) }
```

```latent
// module-part model.lat
import { square, Shape } from "./math.lat";

export class Point {
    x: int;
    y: int;
    fn init(x: int, y: int) { this.x = x; this.y = y; }
    fn norm2() -> int { return square(this.x) + square(this.y); }
}

export fn area(shape: Shape) -> int {
    return match shape {
        case Circle(r): 3 * square(r),
        default: 0,
    };
}
```

```latent
// module-part main.lat
import { Shape } from "./math.lat";
import { Point, area } from "./model.lat";

fn main() -> int {
    let p = new Point(3, 4);
    let c = Circle(2);
    print("norm2 =", p.norm2());
    print("area =", area(c));
    return p.norm2() + area(c);
}
```

Что здесь важно: `model.lat` импортирует только `Shape`, но пользуется
конструктором `Circle` в `match` — импорт enum'а тянет его варианты; `math.lat`
импортируют два файла, но загружается он один раз; `main.lat` — entry, поэтому
только его `main` остаётся функцией `main`, остальные имена манглятся.

Запуск:
```bash
latentc compile main.lat app.wasm   # сборка проекта
latentc check main.lat              # то же без записи файла
latentc bundle main.lat bundle.lat  # плоский исходник
```

Блоки выше помечены маркером `// module-part`: по отдельности они не
компилируются (в них есть `import`), валидатор документации их пропускает — см.
[правила примеров](../tooling/contributing.md#документация-правила-примеров).

## 4. Как работает линковка

Линковка двухфазная. **Загрузка:** DFS от entry по `import`, пути нормализуются
до canonical path, каждый файл разбирается ровно один раз (циклы разрешены —
модуль помечается разобранным **до** обхода своих импортов). **Таблицы:** модули
сортируются по canonical path и получают индексы `m0`, `m1`, …; для каждого
строится таблица `(module, name) → mangled`, а каждый импорт проверяется: модуль
существует, символ экспортирован, локальное имя не занято. **Переписывание:** AST
каждого модуля переписывается по таблицам, узлы `import`/`export` удаляются, всё
склеивается в один `Program`.

Дальше программа идёт в type checker и кодоген без изменений: линкер не добавляет
ни «модульных» инструкций, ни рантайм-резолвера.

### 4.1. Порядок модулей

Состав проекта задаёт DFS от entry, а индексы — сортировка по canonical path.
Для примера выше (`main.lat`, `math.lat`, `model.lat`):

```text
m0 = main.lat     (entry: fn main остаётся main)
m1 = math.lat     square → m1$square, sum_squares → m1$sum_squares, Shape → m1$Shape
m2 = model.lat    Point → m2$Point, area → m2$area
```

Порядок детерминирован: один и тот же набор файлов всегда даёт одни и те же
имена, а значит и одни и те же WASM-байты.

### 4.2. Манглинг имён

Формат — `m<индекс>$<имя>`:

| Что | Как переписывается |
|---|---|
| top-level `fn`/`class`/`enum` | `m1$square`, `m2$Point`, `m1$Shape` |
| `main` entry-модуля | **не** манглятся — именно её экспортирует WASM-модуль |
| варианты enum | `m1$Circle`, `m1$Rect`; переписываются и вызовы `Circle(2)`, и паттерны `case Circle(r)` |
| `new Point` | `new m2$Point` (парсер хранит имя класса с префиксом `new `) |
| методы классов | манглятся существующим механизмом `Class_method` от мангленного имени класса |
| локальные объявления, builtin'ы, импортированные имена | локальные и builtin'ы (`print`, `len`) не манглятся; импортированные заменяются на mangled-имя цели (с учётом алиаса) |

Практическое следствие: две функции `helper` в разных модулях — это разные
символы (`m1$helper` и `m2$helper`), конфликта нет. А два **экспорта** с одним
именем в одном модуле — ошибка ещё на этапе таблиц.

### 4.3. Что видит type checker

Связанный `Program` содержит все функции/классы/enum'ы сразу, поэтому type
checker видит сигнатуры всего проекта: вызов функции из другого модуля
типизируется как обычный вызов, межмодульная рекурсия работает. Отдельного
«модульного» типа или namespace в системе типов нет.

### 4.4. Циклы импорта

Циклы разрешены: `a.lat` ↔ `b.lat` — нормальный проект. Имена разрешаются по
таблицам, а не по порядку исполнения, а top-level код не исполняется вовсе.
Резолвер движка №1 дополнительно возвращает найденные циклы в `cycles`, но
ошибкой это не считает.

## 5. Ошибки

Все ошибки модулей содержат путь файла, а ошибки импорта — ещё и позицию
объявления: `path:line:col: ...`. Точные тексты (Rust-компилятор):

| Текст | Причина |
|---|---|
| `абсолютный путь импорта недопустим: '<путь>'` | путь начинается с `/`, `C:\` или UNC |
| `путь импорта должен оканчиваться на '.lat': '<путь>'` | забыли расширение |
| `путь импорта должен быть относительным ('./' или '../'): '<путь>'` | `import { x } from "math.lat"` |
| `<path>:<L>:<C>: файл не найден: <resolved>` | файла нет по разрешённому пути |
| `<path>:<L>:<C>: символ '<имя>' не экспортирован из '<path>'` | импорт приватного или несуществующего имени |
| `<path>:<L>:<C>: имя '<имя>' уже объявлено в модуле` · `<path>:<L>:<C>: дубликат импортированного имени '<имя>'` | импорт конфликтует с локальным объявлением или импортирован дважды |
| `<path>:<L>:<C>: export '<имя>': объявление не найдено` | `export` повешен на имя, которого нет (внутренняя проверка линкера) |
| `<path>:<L>:<C>: модуль не найден: <resolved>` | файл был в наборе при загрузке, но потерялся при линковке |
| `<path>: файл передан дважды с разным содержимым` · `<path>: entry-файл не найден среди переданных файлов` | в наборе дубликат пути с другим текстом или нет entry |
| `<path>: <ошибка лексера/парсера>` | синтаксическая ошибка в конкретном файле |

Пример вывода CLI:

```text
$ latentc check main.lat
error: main.lat:2:10: символ 'squer' не экспортирован из 'math.lat'
```

Сначала проверяется структура проекта, потом типы; полный каталог —
[диагностики](../reference/errors.md#модули-и-линковка).

## 6. CLI

```text
latentc compile <file.lat> [out.wasm]   — скомпилировать проект в WASM
latentc check <file.lat>                — проверить проект, ничего не записывая
latentc bundle <file.lat> [out.lat]     — плоский Latent-исходник проекта
latentc version | --version | -v        — версия компилятора
```

- Аргумент — **entry-файл**; остальные файлы CLI находит сам, читая `import` с
  диска рекурсивно (циклы безопасны, повторные импорты не читаются дважды).
- `compile` по умолчанию пишет `<вход без .lat>.wasm` и печатает
  `main.lat -> app.wasm (1194 bytes)`; `check` печатает `ok: <N> bytes of wasm`
  (полный проход компиляции, включая кодоген, а не только синтаксис).
- `bundle` без второго аргумента печатает исходник в stdout, с аргументом —
  пишет файл и печатает `main.lat -> bundle.lat (N bytes)`.
- Ошибки — в stderr строкой `error: ...`, код возврата `1`; ошибка чтения файла
  из дерева импортов: `main.lat:3:1: файл не найден: /work/project/util.lat (...)`.

## 7. Модули в web IDE

**Активный файл — это entry.** Остальные `.lat`-файлы workspace доступны как
модули; путь в `import` разрешается относительно активного файла.

- **Движок №1 (JS-интерпретатор)** линкует модули нативно:
  `compiler/modules.js` (канонизация путей, разбор `import`, DFS-граф, кэш
  разобранных модулей по паре «путь + хэш содержимого»), `modules-link.js`
  (двухфазная линковка и манглинг `mN$имя`), `modules-rewrite.js` (переписывание
  AST), `parser-modules.js` (грамматика `import`/`export`).
- **Движок №2 (Rust → WASM)** получает **все** `.lat`-файлы workspace одним
  манифестом `LPF1` (отсортированы по пути, плюс индекс entry) и вызывает
  C-ABI `latent_compile_files`; результат кэшируется по хэшу набора файлов
  (`services/compiler-service-project.js`). Наличие ABI проверяется флагом
  `supportsModules`: старая сборка `compiler.wasm` без него даёт понятное
  «engine #2 пока без модулей» и запуск в движке №1.
- **Run / Run with AI / Check** работают с проектом: Check проверяет и линковку
  (нет файла, символ не экспортирован), Run исполняет все модули в движке №1,
  self-repair правит только entry-файл — остальные считаются библиотечными.
- **Ограничения UI.** Дерево файлов плоское: каталогов нет, а символы
  `/ \ : * ? " < > |` в имени заменяются на `_`, поэтому импорт на практике
  всегда `"./name.lat"`, а `"../x.lat"` за пределы workspace — ошибка
  `module path '...' escapes the project root`. Имена файлов уникальны
  (`main-2.lat`), иначе два файла с одним путём нельзя залинковать.
  Ошибки показываются как `path:line: ...`. Подробнее про IDE —
  [Web IDE](../tooling/web-ide.md#модули-и-многофайловые-проекты).

## 8. Self-hosted компилятор и `bundle`

У self-hosted компилятора (`selfhost/`) **нет файловой системы**: он получает
один исходник в линейной памяти и не умеет читать `import`. Поэтому модули —
фича хоста/линкера, а selfhost потребляет **bundle**:

```bash
latentc bundle main.lat bundle.lat    # хост: линковка + печать
node selfhost/wasm-compiler.mjs compile bundle.lat bundle.wasm
```

Что делает `bundle`:

- печатает связанный `Program` обратно в Latent: `import`/`export` удалены,
  модули идут в порядке canonical path (тот же детерминированный порядок);
- `$` в именах (`m1$square`) заменяется на `__` (`m1__square`), потому что
  лексер selfhost принимает только `[A-Za-z_][A-Za-z0-9_]*`;
- печать детерминирована, поэтому `bundle` одного проекта всегда одинаков.

Selfhost остаётся однофайловым (его собственный `shc.lat` — один файл), но может
собрать **любой** многофайловый проект, если хост сделал `bundle`. Проверка —
дифференциальный тест `selfhost/test/modules.test.mjs` на фикстурах
`selfhost/test/fixtures/modules/`: `latentc compile(bundle)` байт-в-байт равен
`latentc compile_files(entry)`, а selfhost на том же bundle даёт тот же `main()`
и тот же статус ошибок. Побайтового равенства **между Rust и selfhost нет и не
требуется** — их кодогенераторы исторически расходятся даже на однофайловом
`fn main() -> int { return 42; }`; подробности и таблица размеров — в
[self-hosted компиляторе](../specs/selfhost.md#модули-и-bundle).

## 9. Ограничения v1

| Чего нет | Что делать |
|---|---|
| `export *`, `export { x } from ...` (re-export) | импортировать имена по одному в каждом модуле |
| `import * as ns` | импортировать нужные имена явно |
| динамических `import()` | модули статичны; код всегда в сборке |
| пакетного менеджера, `node_modules`, внешних пакетов | только файлы проекта |
| абсолютных путей и URL в `import` | относительный путь от импортёра |
| импорта без расширения (`.lat`) | указывать расширение всегда |
| каталогов в web IDE | плоские имена файлов |
| отдельного namespace/квалификации (`math.square`) | имена импортируются «плоско», конфликты решаются алиасами |

## 10. Модули, чанки и бандлеры

Это разные уровни, и они не конфликтуют: файловые модули Latent сворачивает
линкер компилятора (на выходе **один** WASM-модуль на проект), а ленивые чанки
делает ваш сборщик (Vite/Rollup/webpack) — несколько `.js`/`.wasm`-ассетов,
загружаемых по действию пользователя.

После линковки `import` не превращается в сетевой запрос. Дробить на чанки нужно
сам рантайм — `.wasm` ядра грузить через `dynamic import()` вокруг загрузчика, а
не в стартовом бандле. Практические приёмы (Vite `?url`,
`new URL(..., import.meta.url)`, `manualChunks`, бюджеты размера) — в
[гайде по фронтенду](./web-and-frontend.md#68-ленивая-загрузка-и-чанки).

**Модули — про структуру кода, чанки — про момент загрузки**: линкер убирает
модульную границу до WASM, бандлер добавляет сетевую границу после.

## Термины

- **движок №1** — JS-интерпретатор в web IDE: исполняет язык, включая host-фичи.
- **движок №2** — Rust-компилятор (`src/`), собранный в `compiler.wasm`:
  компилирует подмножество языка в WASM.
- **type checker** — проход проверки типов (`src/typechecker/`), общий для одного
  файла и для связанного проекта.
- **runtime** — исполнение программы: host-рантайм движка №1 или WASM-рантайм
  браузера.
- **линкер (linker)** — `src/modules/linker.rs`: таблицы экспортов, манглинг,
  сборка единого `Program`.
- **bundle** — плоский Latent-исходник всего проекта (`m1__square`), вход
  selfhost-компилятора.
- **fixed point** — свойство selfhost: `stage2 === stage3` побайтово.
